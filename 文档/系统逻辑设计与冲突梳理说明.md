# 皮肤组织病理报告系统 - 业务逻辑设计与冲突梳理说明书

> **文档版本**：v1.4.0  
> **适用范围**：报告制作、报告审核（待审核/重切）、独立免疫组化（IHC）、报告输出三列表及签名单系统全链路逻辑与防冲突规范  

---

## 1. 系统整体逻辑架构模型

本系统采用 **本地原生轻量 WebUI + Python 核心业务引擎 + SQLite 双表持久化 + 分层文件系统隔离归档** 架构，所有业务数据与报告文档均严格限定在用户指定的工作目录中：

```
                     ┌────────────────────────────────────────────────────────┐
                     │                      本地 Web 交互界面                  │
                     │ (录入 / 制作 / 审核 / 免疫组化 / 输出 / 签名单 / 查询)   │
                     └───────────────────────────┬────────────────────────────┘
                                                 │ HTTP / REST API
                                                 ▼
                     ┌────────────────────────────────────────────────────────┐
                     │                    Python 核心服务层                    │
                     │ (路由调度、排版引擎、双轨归档事务、照片同步、占锁检测)   │
                     └───────────────┬──────────────────────────┬─────────────┘
                                     │                          │
                      ┌──────────────┴──────────┐        ┌──────┴───────────────────────┐
                      ▼                         ▼        ▼                              ▼
        ┌──────────────────────────┐      ┌──────────────────────────────────────────────────┐
        │     SQLite 双表模型       │      │              本地工作目录文件系统                   │
        │ patients + ihc_reports   │      │ (未归档报告 / 已归档报告 / 特殊患者归档 / 领取表)   │
        └──────────────────────────┘      └──────────────────────────────────────────────────┘
```

## 2. 工作目录拓扑规范与职责定义

说明文档统一置于软件包根目录 `文档\` 下；工作目录保持业务数据纯净，目录职责如下：

| 目录路径 | 职责与归档定义 | 读写与隔离策略 |
| :--- | :--- | :--- |
| `.\未归档报告\病理报告录入\` | 初次录入生成的初始草稿（`病理号_姓名.docx`） | 【录入】写入；【信息修改】自动更名与同步 |
| `.\未归档报告\病理报告输出\` | 原报告（含待审核/重切）成品草稿（`病理号_姓名_诊断.docx`） | 【报告制作】与【报告审核】双向同步覆盖；更名诊断时清理旧诊断草稿 |
| `.\未归档报告\病理照片\` | 患者原显微镜照片文件夹（`病理号_姓名\`） | 制作区读取；审核复制目录新增图片会在审核保存时回同步至此 |
| `.\未归档报告\临床照片\` | 患者大体/皮损临床照片目录 | **唯一临床照片源目录**；制作、审核、组化三模块【临床照片查询】均直接打开此目录，**不再向特殊归档复制** |
| `.\已归档报告\` | **全科正式归档报告平铺库**（无子目录、不复制照片） | 原报告为 `病理号_姓名_诊断.docx`；免疫组化新报告为 `<原归档stem>_免疫组化报告.docx`，同一患者两份并存 |
| `.\特殊患者归档\待审核\` | “待审核”患者同期同步草稿文件夹（仅含 `[病理报告]...docx` 与 `病理照片\`，**无临床照片**） | 制作与审核保存时双向完全同步；审核完成并在制作区归档后移入 `完成审核\` |
| `.\特殊患者归档\重切\` | “重切”患者同期同步草稿文件夹（仅含 `[病理报告]...docx` 与 `病理照片\`，**逻辑与待审核完全等价**） | 同 `待审核\`：双向同步草稿、审核读取其复制后 `病理照片\`、归档后移入 `完成审核\` |
| `.\特殊患者归档\完成审核\` | 原 `待审核` / `重切` 经【完成审核】并在制作区归档后的完整留存目录 | 归档后仍可被审核修改同步更新（但不直接改动 `已归档报告\`） |
| `.\特殊患者归档\免疫组化\` | 独立免疫组化报告的工作草稿区（由【免疫组化】模块点击创建后生成，仅含副本 `.docx` 与 `病理照片\`，**无临床照片**） | 仅由【免疫组化】保存操作写入；**独立于原报告，归档时不移入 `完成审核\`，文件仍保留在原目录** |
| `.\领取表\` | 批量生成的 Excel 与无空行 Word 签名单 | 自动计算并标注参考手术日期，默认调用 Word 打印 |
| `.\数据库\pathology.db` | 核心 SQLite 数据库（开启 WAL 模式） | 维护 `patients` 主表与 `ihc_reports` 副表 |

## 3. 核心业务流转三轨时序

### 3.1 轨道一：常规患者与“仅标注需免疫组化”的原报告
1. **登记录入**：输入患者信息、图片数（1-9）及送检部位 $\rightarrow$ 生成 `病理报告录入\` 初稿与 `病理照片\` 目录。
2. **报告制作**：选中显微照片（单图自动去序号、多图保留序号）、套用模板、勾选或保持状态。
   - 若**仅勾选 `[ ] 需免疫组化`**（未勾选 `待审核`/`重切`），原报告**视同普通报告**：保存时**不**自动创建 `特殊患者归档\免疫组化\`，允许直接在制作区预览、打印第 1 页并【一键归档】。
3. **平铺归档与输出**：点击归档后写入 `已归档报告\病理号_姓名_诊断.docx`，进入【报告输出】列表 1（常规已归档）。同时该患者列入 🧪【免疫组化】模块左侧列表，等待后续创建第二份免疫组化报告。

### 3.2 轨道二：待审核与重切患者（二者逻辑完全等价）
1. **制作保存触发分流**：
   - 在【报告制作】勾选 `待审核` 和/或 `需重切` 并保存时，系统更新 `未归档报告\病理报告输出\`，并将该文档与 `病理照片\` 复制到 `特殊患者归档\待审核\`（和/或 `重切\`），**严禁复制临床照片目录**。
   - **禁止制作区直接归档**：前端与后端（`source="maker"`）同时拦截尚未完成审核的 `待审核` / `重切` 报告直接归档。
2. **审核区协同操作（`待审核` 队列，不含纯免疫组化患者）**：
   - **照片查找规则**：【临床照片查询】打开 `未归档报告\临床照片\`；【病理照片目录】打开与复制路径指向复制后的 `特殊患者归档\待审核（或重切）\<患者目录>\病理照片\`，【重新读取照片】扫描该复制目录。
   - **双草稿双向完全同步**：在【报告审核】修改报告医生、审核医生、报告日期、照片排版、镜下所见或诊断后保存：
     1. 将复制到审核目录的新增照片回同步至 `未归档报告\病理照片\`（及兄弟队列目录），并将选中图路径规范化以免后续移出队列或切换制作区时丢图；
     2. **同步覆盖** `未归档报告\病理报告输出\` 与 `特殊患者归档\(待审核 | 重切 | 完成审核)\` 两份草稿（更名诊断时自动清理旧诊断草稿）；
     3. **不直接修改 `已归档报告\`**：若此前已归档（`archived=1`），本次保存自动将其设为 `archived=2`（需重新归档）。
     *(对称地，当上述患者在【报告制作】重新保存时，也会同步更新 `特殊患者归档\待审核（或重切/完成审核）\` 中的草稿与照片。)*
   - **完成审核与返制作区归档**：点击【✅ 完成审核】置 `review_status='完成审核'`；随后前往【报告制作】点击【📦 一键归档】，将原报告写入 `已归档报告\` 并把 `待审核`/`重切` 目录移入 `特殊患者归档\完成审核\`。

### 3.3 轨道三：独立免疫组化报告（同一患者的第二份独立报告）
1. **创建前提与初始化**：在 🧪【免疫组化】模块点击【创建免疫组化报告】，系统校验证明患者**原报告已在 `已归档报告\`** 后，复制原已归档 `.docx` 与 `未归档报告\病理照片\` 至 `特殊患者归档\免疫组化\<原归档文件名stem>\`（**不复制临床照片**），并在 `ihc_reports` 建档。
2. **独立编辑与保存**：提供报告医生、审核医生、报告日期、镜下所见、诊断与复制目录照片插槽编辑，以及一键打开/复制组化 `病理照片\` 路径和【临床照片查询】。点击【保存】仅重写 `特殊患者归档\免疫组化\` 内的 `.docx` 与 `ihc_reports`，**完全不影响 `patients` 主表及原报告（未归档/已归档均不动）**；若该免疫组化报告此前已归档，保存后 `ihc_reports.archived` 置为 `2`。
3. **独立归档与输出**：点击【归档】仅将组化 `.docx` 复制到 `已归档报告\<原归档文件名stem>_免疫组化报告.docx`，与原报告并存不覆盖；**不移动 `特殊患者归档\免疫组化\` 目录，不进入 `完成审核\`**。在【报告输出】列表 3（免疫组化已归档）支持独立预览、打印第 1 页及独立撤销组化归档。

*(注：若患者同时标注了 `待审核`/`重切` 与 `需免疫组化`，原报告进入【报告审核】走轨道二完成审核与归档后，患者仍在 🧪【免疫组化】列表保留，继续按轨道三出具独立免疫组化报告，两条链路互不误删、并行不悖。)*

## 4. 关键逻辑冲突排查与防冲突设计

经过对新版多轨流转的系统性梳理，共消除以下 **10 大核心逻辑冲突**：

### 冲突 1：待审核/重切禁归档 vs 纯免疫组化允许常规归档
- **潜在冲突**：以往把“需免疫组化”视同“待审核”，导致仅需免疫组化的患者无法先出具原初诊报告。
- **消解方案**：拆分标注判定规则——前端与后端 `/api/reports/archive` 仅拦截未完成审核的 `待审核` 与 `重切`；仅勾选 `需免疫组化` 视作普通报告直接流转并可常规归档与打印，同时勾选时按 `待审核`/`重切` 约束原报告归档。

### 冲突 2：双报告同人重名覆写与完成审核目录混杂冲突
- **潜在冲突**：同一位患者有“免疫组化前原报告”和“免疫组化后报告”两份报告，直接归档会互相覆盖，或错误将其移入 `特殊患者归档\完成审核\`。
- **消解方案**：`已归档报告\` 对组化报告强制追加 `_免疫组化报告` 后缀实现并存；常规/审核的保存、归档、覆写与撤销全部排除 `*_免疫组化报告.docx` 和 `特殊患者归档\免疫组化\`；组化归档亦不移动 `特殊患者归档\免疫组化\`，绝不进入 `完成审核\`。

### 冲突 3：审核保存 vs “必须去制作区重新归档”机制冲突
- **潜在冲突**：若审核保存既将数据库置 `archived=2`（提示去制作区重归档），又偷偷覆写 `已归档报告\`，会导致“未确认重归档即篡改封存文件”的自相矛盾。
- **消解方案**：**彻底统一规则**——`POST /api/reviews/save` 仅双向同步 `未归档报告\病理报告输出\` 与 `特殊患者归档\(待审核 | 重切 | 完成审核)\` 两份草稿，**绝不提前改写 `已归档报告\`**；已归档病例修订后保持 `archived=2`，必须前往【报告制作】点击【一键归档】才会更新 `已归档报告\`。

### 冲突 4：审核复制目录新增图片 vs 制作区切换或归档后丢图冲突
- **潜在冲突**：审核区读取复制目录 `特殊患者归档\待审核（或重切）\...\病理照片\` 的新增图片（如重切新图），若直接把该临时路径写入 `patients.selected_images`，切换回制作区或归档后路径迁移时图片会丢失。
- **消解方案**：审核保存时通过 `sync_review_photos_to_making_and_siblings` 把审核目录新增图片同步回 `未归档报告\病理照片\` 及兄弟队列，并将数据库图片路径规范化到稳定的未归档路径；同时前端 `findMatchingPhoto` 与标签切换强制重载（`loadMakingPatients(true)` / `loadReviewPatients(true)`）支持路径和文件名双匹配。

### 冲突 5：诊断更名后的残留草稿文件夹与文件堆积冲突
- **潜在冲突**：制作或审核区更改患者病理诊断后，旧诊断对应的 `病理报告输出\..._旧诊断.docx` 或 `特殊患者归档\...\..._旧诊断\` 残留造成同一患者两套草稿并存。
- **消解方案**：引入 `cleanup_stale_output_reports` 与 `_sync_folder_to_special_category` 事务替换逻辑，在诊断更名时自动迁移已有照片到新目录并安全删除旧诊断文件/目录。

### 冲突 6：完成审核未归档前在审核区二次保存误删待审目录冲突
- **潜在冲突**：患者先点【✅ 完成审核】（`is_pending_review` 变为 `0`）但尚未在制作区归档，若再次点击审核保存，`save_special_draft_queue` 按常规“未勾选则删”逻辑会误删尚未移动的 `待审核` 文件夹。
- **消解方案**：在 `/api/reviews/save` 与 `/api/reports/save` 中区分 `review_status == '完成审核'` 状态——走 `sync_updated_report_to_special_archives` 原地刷新已有草稿文件夹（无论其当前在 `待审核`、`重切` 还是已移至 `完成审核`），并在 `update_patient_report_making` 中保留 `完成审核` 状态（不被兼有的 `is_needs_ihc` 覆盖）。

### 冲突 7：多院区/特殊病理号前缀独立计数与主键冲突
- **消解方案**：带前缀病理号字符串（`L`/`B`/`H`/`T` 或无前缀）作为 SQLite 唯一主键，按 `(前缀 + 送检日期)` 独立分区从 `01` 递增且录入查重强拦截。

### 冲突 8：信息变更（姓名/病理号/基础资料修改）级联更新与重归档询问
- **消解方案**：`PUT /api/patients/<old_no>` 同步更新数据库、录入草稿、病理照片目录、输出报告及所有 `特殊患者归档`（含 `待审核`、`重切`、`完成审核` 与 `免疫组化` `ihc_reports`），**绝不直接改写 `已归档报告\`**；保存后按需询问是否立即重新归档或置为 `archived=2`。

### 冲突 9：Word 排版线条重叠、固定 15 磅行距与单页第 1 页硬件打印保护
- **消解方案**：自动清除表格上方 VML 浮线、保护表格底边、固定 15 磅行距并按 1/2/3/4-6/7-9 图补偿行数（15/10、14/10、15/10、10/6、5/3），确保第 1 页固定止步于医生签名栏，全部打印调用 Word COM 严格输出第 1 页，病史存第 2 页作电子留档。

### 冲突 10：文件排他锁检测、WAL 并发防锁与 Windows 回收站软删除
- **消解方案**：写入 Word（含制作/审核/组化/归档各节点）与 Excel 前执行排他打开检测，被 Word/WPS 占用则返回 HTTP 409 中文指引；SQLite 启用 WAL 模式与 15s 忙等待；所有文件清理调用 Windows Shell 软删除至回收站。
