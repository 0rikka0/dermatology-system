# 皮肤组织病理报告系统 - 业务逻辑设计与冲突梳理说明书

---

## 1. 系统整体逻辑架构模型

本系统专为医院皮肤科组织病理诊断全流程设计，采用 **本地原生轻量 WebUI + Python 核心业务引擎 + SQLite 数据库持久化 + 规范化文件系统分层归档** 的架构。系统定位为**绿色免安装、免环境配置**的便携式独立软件，所有文件读写均严格限定在用户指定的工作目录中。

```
                              ┌─────────────────────────────────────────┐
                              │            本地 Web 交互界面            │
                              │ (录入 / 制作 / 审核 / 输出 / 签名单 / 查询) │
                              └────────────────────┬────────────────────┘
                                                   │ HTTP / REST API
                                                   ▼
                              ┌─────────────────────────────────────────┐
                              │           Python 核心服务层             │
                              │  (路由调度、排版引擎、归档逻辑、数据校验)  │
                              └───────┬─────────────────────────┬───────┘
                                      │                         │
                     ┌────────────────┴────────┐       ┌────────┴──────────────┐
                     ▼                         ▼       ▼                       ▼
          ┌─────────────────────┐   ┌──────────────────────────────────────────────┐
          │   SQLite 数据库     │   │              本地工作目录文件系统             │
          │ (pathology.db 状态机)│   │ (未归档报告 / 已归档报告 / 特殊患者归档 / 领取表) │
          └─────────────────────┘   └──────────────────────────────────────────────┘
```

## 2. 工作目录拓扑规范与职责定义

系统在首次启动时引导用户选定根工作目录，并自动建立标准化子目录，禁止平铺混杂（说明文档则直接位于软件包根目录 `文档\` 下，工作目录纯净用于业务数据）：

| 目录路径 | 职责与归档定义 | 读写权限与控制策略 |
| :--- | :--- | :--- |
| `.\未归档报告\病理报告录入\` | 存放患者信息初次录入后生成的草稿 Word 报告（`病理号_姓名.docx`） | 仅在【录入】阶段写入；【信息修改】时同步重命名 |
| `.\未归档报告\病理报告输出\` | 存放排版完成的最终 Word 报告（`病理号_姓名_诊断.docx`） | 【报告制作】与【报告审核】保存时生成或覆盖；只读查看 |
| `.\未归档报告\病理照片\` | 按患者存放显微镜导入的照片文件夹（`病理号_姓名\`） | 外部显微拍照软件存入；系统只读扫描读取与缩略图加载 |
| `.\未归档报告\临床照片\` | 存放患者门诊或术中拍摄的临床照片（`姓名\` 专属文件夹） | 仅供系统检索定位；支持模糊匹配与重名提示唤醒 |
| `.\已归档报告\` | **常规患者及已完成审核患者的最终报告平铺归档库**（`病理号_姓名_诊断.docx`） | 归档时直接存入最终报告，无子文件夹，无前缀，不复制照片，彻底杜绝磁盘膨胀 |
| `.\特殊患者归档\待审核\` | 存放标记为“待审核”的未审阅患者独立档案副本（含报告、病理与临床照片） | 制作保存时自动入库；审核归档后自动从中移除（取出） |
| `.\特殊患者归档\免疫组化\` | 存放标记为“免疫组化”的待补充检验患者独立档案副本（含报告、病理与临床照片） | 制作保存时自动入库；审核归档后自动从中移除（取出） |
| `.\特殊患者归档\重切\` | 存放标记为“重切”的待重切复核患者独立档案副本（含报告、病理与临床照片） | 制作保存时自动入库；审核归档后自动从中移除（取出） |
| `.\特殊患者归档\完成审核\` | 存放原特殊患者经专家审核通过并归档后的完整档案（含报告、病理与临床照片） | 审核通过并归档时自动转入；作为特殊已审档案永久存底 |
| `.\领取表\` | 存放批量生成的 Excel 与 Word 报告领取签名单（`报告领取签名单_时间.xlsx / .docx`） | 签名单生成器自动写入；默认调用 Word 打印无空行签名单 |
| `.\数据库\` | 存放核心 SQLite 数据库（`pathology.db`） | 开启 WAL 模式，维持全系统患者主表、状态机、审计追踪与并发读写 |

## 3. 核心业务流程与文件流转时序

### 3.1 常规病例全生命周期流转
1. **登记录入**：输入基础信息（年龄支持 `岁/月/日` 与 `自由输入`；`H/T` 前缀支持修改送检单位与科室），选定图片数（1~9）及送检部位 $\rightarrow$ 自动提取送检日期并编号 $\rightarrow$ 生成草稿 Word 报告存入 `未归档报告\病理报告录入` $\rightarrow$ 建立照片文件夹于 `未归档报告\病理照片` $\rightarrow$ 数据库登记 `archived=0, review_status='未审核'`；选中列表患者可一键查询临床照片。
2. **报告制作**：按病理号正序读取列表 $\rightarrow$ 导入显微图片（单图自动合成病理诊断默认去序号，多图保留序号） $\rightarrow$ 智能推荐镜下描述模板 $\rightarrow$ 点击保存 $\rightarrow$ 生成排版完成的成品 Word 存入 `未归档报告\病理报告输出`。
3. **平铺归档**：点击归档 $\rightarrow$ 报告直接平铺存入 `已归档报告\病理号_姓名_诊断.docx`（无子目录，无前缀，不向归档复制照片，保护磁盘空间） $\rightarrow$ 数据库置 `archived=1`。
4. **报告输出**：在【报告输出】列表 1（常规已归档）中集中查阅、调用 Word COM 引擎单页打印或今日批量打印第 1 页。

### 3.2 疑难/特殊病例（待审核、免疫组化、重切）流转时序
1. **制作阶段标记**：医生在报告制作工作区勾选【待审核】、【免疫组化】或【重切】。
2. **保存与自动分流**：
   - 点击保存报告时，系统更新数据库为相应标记（如 `待审核`、`免疫组化`、`重切` 或组合状态）。
   - **自动流转至特殊待审队列**：系统将已排版的报告及照片自动打包备份放入 `.\特殊患者归档\待审核\`、`免疫组化\` 和/或 `重切\`。若临床照片匹配多个重名项，弹出警示提示并并发调起两个资源管理器窗口供人工核对复制。
   - **拦截直接归档**：在制作界面点击归档时，系统进行硬性拦截并提示：“必须先由专家完成审核”。
3. **专家审核工作区**：
   - 专家在专属的待审列表中选中病例，调整报告医生、审核医生姓名、报告日期、镜下描述或修正诊断。
   - 点击【保存修改并同步覆盖各归档】：穿透同步覆盖 `未归档报告\病理报告输出`、`已归档报告` 以及 `特殊患者归档` 下的所有现有副本。
   - 审阅完毕点击【完成审核】：状态置为 `review_status='完成审核'`（审核界面不设“打包归档”按钮）。
4. **审核后正式归档**：
   - 返回【报告制作】列表后，“完成审核未归档”的病例以独立区分底色及 **“需重新归档”** 标签提醒；操作人员核验后点击【一键归档】：
   - **取出逻辑**：系统自动从 `.\特殊患者归档\待审核\`、`免疫组化\` 与 `重切\` 中移出（删除待审文件夹）。
   - **归档转入**：将最终审定档案完整存入 `.\特殊患者归档\完成审核\病理号_姓名_诊断\`。
   - **常规入库**：同步将最终报告平铺写入 `.\已归档报告\病理号_姓名_诊断.docx`，此后在制作列表中呈现为普通已归档样式。
5. **集中输出**：该患者自动进入【报告输出】列表 2（特殊已审核已归档列表），供专人查验与 Word 单页打印。

## 4. 关键逻辑冲突排查与防冲突设计

经过对系统文件读写、并发操作、状态跳转与业务场景的全面梳理，本系统识别并彻底消除了以下 9 大核心潜在逻辑冲突：

### 冲突 1：特殊患者与常规患者归档时机的冲突
- **潜在冲突**：初级医生制作报告并标记为“待审核”后，若随手点击“一键归档”，可能导致未审阅报告被提前打包装箱，甚至流向临床打印。
- **消解方案**：
  1. **前端阻断**：制作界面在点击归档时，检测当前勾选框状态或数据标记，若为待审核/免疫组化，立即弹出严禁归档的指导警告，终止执行。
  2. **后端强制约束**：API 接口接收参数 `source: "maker"`，并在服务端严格核查；若未完成审核，坚决返回 HTTP 400 拒绝归档。
  3. **保存即分流**：点击保存时即自动拷贝到 `特殊患者归档\待审核` 供专家调阅，无需也严禁在制作区归档。

### 冲突 2：审核归档后的目录重复堆积与状态不一致冲突
- **潜在冲突**：如果患者审核完成归档后，旧的草稿档案仍然残留在 `特殊患者归档\待审核` 中，会导致待审列表出现“幽灵记录”；若只存入 `完成审核` 而漏掉 `已归档报告`，会导致全科总病历库缺件。
- **消解方案**：
  - 归档执行严格的**“取出并转移”**事务：
    1. 扫描并彻底清理 `特殊患者归档\待审核` 和 `特殊患者归档\免疫组化` 中该病理号的所有残留目录。
    2. 将包含最终报告及照片的完整归档包写入 `特殊患者归档\完成审核`。
    3. 同步无缝平铺写入常规总库 `已归档报告`。
    4. 状态机原子更新为 `archived=1, review_status='完成审核'`。

### 冲突 3：多次保存与已归档文件的静默覆盖冲突
- **潜在冲突**：一份病理报告在归档后，如果医生在制作工作区重新打开并误触保存，可能悄然覆盖已入库的历史归档，破坏归档的法定严肃性。
- **消解方案**：
  - **制作区保存**：仅允许覆盖工作区输出的 `未归档报告\病理报告输出`，**坚决不触碰** `已归档报告`。
  - **状态自适应降级**：若该病理已归档，重新保存排版后，系统自动在数据库中将其归档状态标记为 `archived=2`（**需要重新归档**），醒目标红提示，必须由经办医生核验后重新归档方可更新归档库。
  - **审核区保存特权**：唯独在【报告审核】工作区中，专家的保存被赋予“权威穿透同步”属性，执行时遍历所有关联目录并全量刷新。

### 冲突 4：多院区/特殊病理号前缀独立计数与主键冲突
- **潜在冲突**：系统存在普通号（如 `2026110301`）以及含字母前缀的病理号（如陆港 `L2026110301`、病房 `B2026110301`、特殊 `T2026110301`）。若全局共享流水号，会导致院区序号断号；若序号重叠而主键未加前缀，会导致数据库冲突。
- **消解方案**：
  - **复合编号主键机制**：病理号字符串（含前缀，如 `L2026110301`）直接作为 SQLite 主键。
  - **独立序列提取算法**：编号生成器按 `(前缀 + 送检日期 8 位)` 进行独立分区统计流水号，普通号与各前缀号互不干扰、独立从 01 递增，彼此共存且绝不冲突。
  - **录入重复强校验**：录入时实时检测，若主键重复则弹出警告并显示已存在患者姓名，严禁盲目覆写。

### 冲突 5：信息变更（姓名/病理号/基本信息修改）与历史档案的同步及防静默覆写冲突
- **潜在冲突**：已保存或已归档患者在录入页修改姓名、病理号、年龄、临床诊断等基础信息后，若仅修改数据库或草稿文件，会导致成品输出报告、照片路径及特殊归档目录与数据库脱钩；而若直接覆写 `已归档报告`，又违背了归档档案的人工确认原则。
- **消解方案**：
  - 提供 `rename_patient_files_and_folders` 与 `sync_updated_report_to_special_archives` 事务调度：修改患者信息保存时，自动同步更新数据库（含照片路径映射）、草稿 Word、病理照片文件夹、成品输出 Word 及 `特殊患者归档` 下所有相关目录名与报告文件内容，**严禁直接改动 `已归档报告` 目录内容**。
  - 若该病例此前已保存成品报告或已归档（且不处于未审挂起状态），系统保存后主动弹窗询问是否立即重新归档：点击“确定”自动调用归档流程更新 `已归档报告`；点击“取消”则将状态置为 `archived=2`（**需要重新归档**），共享后续防篡改提醒机制。

### 冲突 6：撤销归档与撤销审核的状态回滚与残留冲突
- **潜在冲突**：在输出工作区撤销归档或撤销审核时，若仅修改数据库字段而未清理文件，磁盘将残留冗余归档包；若清理过度，会导致待审文件丢失。
- **消解方案**：
  - **撤销归档**：将数据库置为 `archived=0`，安全删除 `已归档报告` 中的单文件及 `特殊患者归档\完成审核` 中的对应目录，若患者原属于待审或免疫组化，安全保留或恢复其待审副本。
  - **撤销审核**：将状态置回 `待审核`（或保留原 `免疫组化`/`重切` 组合标记），自动从 `完成审核` 中移出，重新安放回 `特殊患者归档` 对应队列，患者无缝重现于审核工作区待办列表中。

### 冲突 7：Word 排版中的线条重叠、图片失衡与分页越界冲突
- **潜在冲突**：
  1. 表格上方原有浮动 VML 直线与三线表顶边重合，呈现难看的双重黑线。
  2. 文字过多或过少导致医生签名行漂移到第二页，或病史无法稳定停留在第二页。
- **消解方案**：
  - **清除浮动线条**：文档生成引擎遍历文档元素，定向清除表格上方所有 `<v:line>` 绘图元素，三线表由标准表格边框呈现，顶底各一根清晰实线。
  - **固定 15 磅行距**：镜下描述与诊断区域彻底禁用不稳定的倍数行距，统一步长为精确的 15 磅（`Pt(15)`）。
  - **各规格行数精密对齐**：图片下方固定留白 1 行；按照单图（15/10）、双图（14/10）、三图（15/10）、4-6图（10/6）、7-9图（5/3）基准严格填充空行，在末尾插入绝对分页符，从物理底层彻底保障**“签名绝对在第一页底端，病史绝对在第二页顶端”**。

### 冲突 8：临床照片模糊检索重名冲突与人工介入机制
- **潜在冲突**：临床照片目录仅命名为患者姓名，不可避免存在同名患者（重名）。若系统盲目归档或误读照片，将导致严重医疗错配；若直接报错，则操作受阻。
- **消解方案**：
  - **查照检索重名**：若匹配到 >1 个同名文件夹，系统明确判定为重名，弹出包含候选目录列表的警示弹窗，并自动打开临床照片母目录供人工核验。
  - **特殊归档重名双窗口联动**：特殊患者归档时若遇重名，系统自动并发打开临床照片母目录和目标归档子目录，让操作员直观对照并手动拖拽归档。

### 冲突 9：文件独占锁、并发死锁与系统崩溃隐患
- **潜在冲突**：医生正在 Word/WPS 中打开报告时系统尝试写入导致崩溃；多线程同时操作 SQLite 导致死锁；删除文件时直接永久物理抹除导致误删不可恢复。
- **消解方案**：
  - **排他写入锁安全探测**：保存前探测文件锁，遭遇占用时提前捕获并转换为中文友好弹窗，防止崩溃。
  - **SQLite WAL 模式与 15s 超时**：开启预写日志并发读写与 busy_timeout 15000ms，彻底规避锁死。
  - **Windows 回收站软删除**：封装安全删除管道，所有删除优先投入系统回收站，防范误删事故。

## 5. 软件运行安全与脱敏机制规范

1. **零安装绿色便携**：
   - 依赖内置于发布包中的嵌入式 Python 运行时与纯净依赖轮子（`python-docx`, `lxml`, `openpyxl`, `et_xmlfile`），不向客户机写入注册表，不依赖系统环境变量，解压即用。
2. **安全删除与回收机制**：
   - 界面上所有的删除操作（如删除报告、移出条目）均配备二次确认模态窗，明确列出即将被清除的文件范围，防止误触删单。
3. **医院与医生信息脱敏化**：
   - 默认安装包不预置任何真实三甲医院的敏感抬头或医生私有信息，系统在初次引导及设置页中均提供动态配置项（送检单位、科室、报告医生、审核医生），文书示例及技术文档统一采用合规假名展示。
